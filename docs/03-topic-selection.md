# 研愿：校园调研与志愿活动平台

## 1. 选题基本信息

| 项目 | 内容 |
| --- | --- |
| 项目名称 | 研愿：校园调研与志愿活动平台 |
| 项目类型 | 软件工程课程设计 |
| 文档版本 | v0.1 |
| 编写日期 | 2026-11-25 |
| 当前状态 | 待教师审核 |
| 计划团队规模 | 4 人 |
| 过程模型 | 增量式开发，每个增量内完成计划、构建、测试和评审 |
| 外部集成点 | GitHub OAuth 第三方登录 |
| 部署目标 | 公网可访问，用户通过浏览器统一使用 |

“研愿”中的“研”指校园调研，“愿”指志愿活动。平台根据参与者的兴趣、能力、资格和空闲时间，为其匹配适合的调研或志愿活动，并支持报名、预约、候补、签到、完成确认和参与记录。

## 2. 选题摘要

校园调研和志愿活动通常依赖群聊、共享文档、表单和人工私聊完成招募。参与者很难持续发现适合自己的机会，组织者需要重复筛选人员、确认时间和补录空缺。

本平台将调研参与者和志愿者招募统一抽象为“校园参与机会”，提供一条完整流程：

```text
组织者发布参与机会
  -> 参与者维护兴趣、技能和空闲时间
  -> 系统完成资格与时间匹配
  -> 参与者报名或接受邀请
  -> 组织者确认并锁定名额
  -> 参与者签到
  -> 组织者确认完成
  -> 形成参与记录
```

平台通过统一偏好档案、隐私渐进披露和候补自动补位，减少参与者寻找机会的成本，同时降低组织者的筛选和协调成本。

## 3. 项目背景与问题

### 3.1 参与者面临的问题

- 招募信息分散在多个群聊和问卷链接中，难以持续关注。
- 活动资格、持续时间、地点和参与要求不统一，用户难以快速判断是否适合。
- 为不同类型活动重复填写专业、技能和空闲时间。
- 在确认参与前经常被要求公开联系方式，存在隐私顾虑。
- 取消参与后无法及时找到其他机会。

### 3.2 组织者面临的问题

- 需要人工判断报名者是否符合资格，并反复沟通时间。
- 参与者取消或缺席后，需要重新在群聊中寻找替补。
- 难以判断招募在哪一步流失，例如“符合资格但无人接受邀请”。
- 调研与志愿活动通常使用不同表格，参与记录分散。

### 3.3 当前替代方式

常见替代方式包括群聊广播、问卷星表单、共享在线表格、私聊确认和手工统计。这些方式能够发布信息，但缺乏统一的匹配、隐私、补位和参与记录机制。

## 4. 产品定位与创新点

平台的定位不是通用的校园活动社区，也不是完整的问卷或志愿时长管理系统，而是：

> 面向校园调研和志愿活动的参与机会匹配与预约平台。

主要创新点均来源于用户问题：

### 4.1 统一参与偏好

参与者只维护一份兴趣、技能、资格信息和空闲时间，同时用于调研与志愿活动匹配，避免重复填写。

### 4.2 双向匹配

组织者设置资格、技能、人数和时间要求，参与者维护个人偏好。系统在服务端计算匹配结果，并通过站内推荐或定向邀请呈现，而不是只依赖先到先得的信息列表。

### 4.3 隐私渐进披露

在双方确认预约前，隐藏联系方式、精确地点等敏感字段。确认后仅公开本次参与所需要的信息，并由参与者明确授权。

### 4.4 候补自动补位

参与者取消或邀请超时后，系统释放名额，按照公开规则邀请下一位候补者，并设置接受时限。整个过程由状态机控制。

### 4.5 统一参与记录

平台区分“调研参与完成”和“志愿服务完成”，保留组织者确认记录。志愿时长只作为平台记录，不宣称是学校官方认证时长。

## 5. 用户角色与权限

### 5.1 参与者

目标：找到适合自己的调研或志愿活动，并安全完成参与。

核心权限：

- 创建和维护兴趣、技能、资格信息与空闲时间。
- 浏览、筛选和查看参与机会。
- 接收系统推荐或组织者定向邀请。
- 填写必要的资格信息，报名或接受邀请。
- 选择时段、取消预约和管理候补状态。
- 查看隐私授权范围、签到信息和参与记录。

明确限制：

- 不能查看其他参与者的敏感资料。
- 不能查看组织者后台。
- 不能修改平台公共规则。

### 5.2 组织者

目标：发布调研或志愿活动，并在规定时间与人数内完成人员招募。

核心权限：

- 申请组织者权限并维护组织者资料。
- 创建、编辑、发布和关闭参与机会。
- 配置调研资格或志愿岗位要求。
- 设置预约时段、人数上限和候补规则。
- 查看符合条件人员的匿名匹配结果。
- 发送邀请、确认或拒绝报名。
- 组织签到并确认参与完成。
- 查看招募漏斗和参与统计。

明确限制：

- 只能管理自己创建的机会。
- 未经授权不能查看联系方式和精确地点。
- 不能修改系统级分类、规则和审计记录。

### 5.3 平台运营者

目标：保证平台内容可信、权限可控、数据可追溯。

核心权限：

- 审核或撤销组织者发布权限。
- 管理公共分类、标签和平台规则。
- 处理举报、违规内容和异常账号。
- 配置邀请有效期和候补策略。
- 查看平台统计和审计日志。
- 执行有留痕的账号与权限管理。

明确限制：

- 不能无审计记录地修改用户预约或参与结果。
- 不能随意公开参与者隐私信息。
- 不能代替组织者确认活动完成。

用户可以在符合权限规则的情况下同时参加活动和发布活动，但两类操作使用不同的数据和权限范围。

## 6. 统一业务对象与类型差异

平台的核心对象为“参与机会”，至少包括以下两种类型：

| 类型 | 业务特征 | 特有字段或流程 |
| --- | --- | --- |
| 调研项目 | 招募问卷、访谈或实验参与者 | 资格条件、知情同意、数据用途、参与方式、保密要求 |
| 志愿活动 | 招募校园服务、公益活动和活动协助志愿者 | 服务内容、技能要求、工作时段、签到与完成确认 |

两类机会共用发现、匹配、报名、预约、候补、签到和记录流程，但使用不同的发布字段和完成判定规则。

## 7. 核心业务流程

### 7.1 机会发布

```text
组织者创建草稿
  -> 选择调研或志愿活动类型
  -> 填写基本信息、参与要求和隐私说明
  -> 配置资格规则、名额和时段
  -> 提交发布
  -> 机会进入匹配和报名状态
```

### 7.2 发现与匹配

```text
参与者维护偏好和可用时间
  -> 系统计算可选机会
  -> 展示参与机会和匹配原因
  -> 组织者查看匿名候选者
  -> 发送定向邀请或公开接受报名
```

### 7.3 报名与确认

```text
参与者提交申请或接受邀请
  -> 系统检查资格和名额
  -> 组织者确认
  -> 名额锁定
  -> 双方获得必要的联系方式和参与说明
```

### 7.4 取消与候补

```text
已确认参与者取消
  -> 释放名额
  -> 系统选择下一位候补者
  -> 发送限时邀请
  -> 接受则锁定名额
  -> 超时则继续邀请下一位
```

### 7.5 签到与完成

```text
参与者在规定时间签到
  -> 组织者确认实际参与
  -> 系统生成参与记录
  -> 调研记录参与完成状态
  -> 志愿活动记录服务时段
```

## 8. 核心状态设计

### 8.1 参与机会状态

```text
DRAFT
  -> PUBLISHED
  -> FILLED
  -> IN_PROGRESS
  -> COMPLETED

PUBLISHED/FILLED
  -> CANCELLED
```

### 8.2 报名或邀请状态

```text
INVITED
  -> APPLIED
  -> CONFIRMED
  -> CHECKED_IN
  -> COMPLETED

INVITED/APPLIED
  -> REJECTED
  -> EXPIRED
  -> CANCELLED

CONFIRMED
  -> CANCELLED
  -> NO_SHOW
```

### 8.3 名额状态

```text
AVAILABLE
  -> HELD
  -> BOOKED
  -> RELEASED
```

状态变化必须由后端校验，前端隐藏按钮不能替代服务端权限控制。

### 9.1 身份与个人资料

- GitHub OAuth 和邮箱注册登录。
- 参与者偏好档案。

- 隐私字段授权设置。

### 9.2 参与机会发布

- 创建调研项目或志愿活动草稿。

### 9.3 发现与匹配

- 服务端匹配与匹配原因展示。
- 匿名候选池。
- 站内推荐和定向邀请。

### 9.4 申请、预约与候补

- 报名申请、邀请接受和拒绝。

## 10. 用例规模说明

项目预计形成不少于 24 个用例，主要分组如下：

- 身份与偏好：登录、维护参与者资料、维护组织者资料、配置隐私授权。
- 发现与匹配：浏览机会、组合筛选、查看详情、查看匹配原因、接收邀请。
- 报名与预约：填写资格、提交申请、接受邀请、选择时段、确认预约、取消预约。
- 名额与候补：加入候补、自动递补、邀请超时、释放名额。
- 组织者管理：创建机会、配置资格、发布机会、管理候选者、确认报名、确认完成。
- 运营治理：审核组织者、管理分类、处理举报、查看统计、审计关键操作。

其中至少包含两个非功能需求用例：

1. 多个参与者并发接受最后一个名额时，系统不得超员。
2. 未获得授权的用户不得访问联系方式、精确地点及敏感资格字段。

## 12. 可交付增量

### v0.1 参与机会与偏好

目标：形成可浏览、可发布的参与机会平台。

交付内容：

- 用户认证和基础角色权限。
- 参与者偏好档案。
- 调研与志愿活动统一发布表单。
- 分类搜索、列表和详情展示。
- 基础隐私说明。

验收条件：

- 组织者可以发布两种类型的参与机会。
- 参与者可以筛选并查看机会。
- 不同角色不能访问未经授权的后台。

### v0.2 匹配、预约与候补

目标：完成从匹配到名额确认的核心流程。

交付内容：

- 资格和空闲时间匹配。
- 匿名候选池与定向邀请。
- 报名、确认、取消和名额锁定。
- 候补队列与自动补位。
- GitHub OAuth 外部登录。

验收条件：

- 不符合条件的参与者不能占用名额。
- 同一时段人数不能超过容量。
- 取消或邀请超时后能够正确执行补位。

### v0.3 参与记录、治理与部署

目标：形成可追溯、可治理、可公网演示的完整系统。

交付内容：

- 签到、完成确认和参与记录。
- 敏感字段授权和访问审计。
- 招募漏斗、通知和统计。
- 组织者审核、举报和公共规则。
- 自动化测试、CI/CD、部署和演示脚本。

验收条件：

- 未授权用户不能访问隐私字段。
- 调研和志愿活动均能完成参与记录。
- 关键流程具备单元、集成和验收测试。
- 系统可通过公网地址完整演示。

## 13. 非功能需求

### 13.1 安全性

- 所有业务接口必须执行认证和授权。
- 敏感字段按授权状态动态披露。
- 密码使用安全哈希保存。
- 日志不得记录密码、令牌和完整联系方式。

### 13.2 一致性

- 名额接受使用数据库事务和原子条件更新。
- 取消、候补邀请和名额释放必须保持状态一致。
- 重复提交使用幂等控制。

### 13.3 隐私性

- 参与者在确认前仅看到公开字段。
- 组织者只能访问招募所需的匿名信息。
- 调研原始数据和志愿活动证明材料不进入平台。

### 13.4 可用性与可追溯性

- 匹配原因、名额变化和授权行为应可查询。
- 关键操作必须记录操作者、时间和结果。
- 需求、设计、代码和测试使用统一编号追溯。

## 14. 主要技术风险

### 14.1 并发预约与候补一致性

风险：多个参与者同时接受最后一个名额，或者取消操作与自动补位同时发生。

应对措施：

- 在数据库事务中检查并占用名额。
- 使用版本号或条件更新避免超员。
- 使用显式状态机控制邀请、确认、取消和超时。
- 编写并发集成测试。

### 14.2 隐私字段越权访问

风险：组织者或普通用户通过接口直接访问联系方式、精确地点等隐藏字段。

应对措施：

- 按角色和预约状态执行字段级授权。
- 敏感字段不直接返回前端。
- 对访问关键隐私字段的行为写入审计日志。

### 14.3 虚假或低质量招募

风险：恶意账号发布虚假调研或不合适的志愿活动。

应对措施：

- 组织者发布权限申请与运营者审核。
- 举报、暂停和撤销发布权限。
- 公示平台规则和参与限制。

## 15. 外部集成与部署

### 15.1 外部集成

- 使用 GitHub OAuth 作为第三方登录点。
- 系统同时支持普通邮箱注册，避免只有 GitHub 用户才能参与。
- 不依赖学校统一身份认证、教务系统、实验室系统或志愿时长系统。

### 15.2 技术方向

| 层次 | 拟采用技术 |
| --- | --- |
| 后端 | Java 21、Spring Boot 3、Spring Security |
| 数据访问 | Spring Data JPA 或 MyBatis-Plus |
| 数据库 | PostgreSQL（由团队评审后也可调整） |
| 数据库迁移 | Flyway |
| 前端 | Vue 3、Vite |
| 测试 | JUnit 5、Mockito、Testcontainers |
| 部署 | Docker Compose、Nginx |
| 协作 | GitHub Issues、Projects、Pull Requests、Actions |

### 15.3 公网部署

- 前端静态资源、后端服务、数据库和反向代理通过 Docker Compose 部署。
- 用户可以访问统一公网域名，无需安装客户端。
- GitHub Actions 在推送后执行测试与构建，并支持部署流水线。
- 每个增量创建 Release，对应 v0.1、v0.2、v0.3。

## 16. 范围外内容

- 不保存问卷原始答案、访谈录音、视频或实验数据。
- 不替代正式研究伦理审批。
- 不提供学校官方志愿时长认证。
- 不接入学校学生档案和统一身份认证。
- 不处理真实支付、劳务费用或商品交易。
- 不建设公开聊天广场、内容流或社交关系链。
- 不使用 AI 自动决定报名资格或代替组织者确认完成。

## 17. 需求验证计划

选题中的用户问题必须通过真实访谈确认，不能把团队判断直接写成最终需求。

建议访谈对象：

- 5 至 8 名参加过问卷、访谈或志愿活动的学生。
- 2 至 3 名组织过课程调研、社团志愿活动或访谈的发布者。
- 1 至 2 名负责活动审核、名单管理或平台运营的人员。

重点核实：

- 最近一次寻找参与机会或招募参与者的真实过程。
- 当前使用的群聊、表格和问卷工具。
- 筛选、确认、取消和补位所花费的时间。
- 是否发生过重复联系、信息泄露、爽约或名额空缺。
- 参与者决定是否报名时最关心的字段。

待验证假设：

1. 参与者最关心资格、时长、地点、参与要求和隐私，而不只是信息数量。
2. 组织者的人工筛选和时间协调成本足以支撑匹配与候补机制。
3. 确认后再披露联系方式，能够提高参与者接受邀请的意愿。
4. 统一偏好档案能够减少参加调研和志愿活动时的重复填写。

只有获得访谈或观察证据的痛点才进入需求基线。未被验证的假设应保留为待确认项。

## 19. 过程模型选型

项目采用增量式开发，并在每个增量内进行“计划—构建—测试—评审”迭代。

选择原因：

- 参与机会发布、匹配预约和隐私治理可以分阶段交付。
- 每个增量都能形成可运行、可评审版本。
- 并发一致性、候补补位和隐私授权等高风险问题可以集中验证。
- 便于根据真实访谈和阶段评审调整需求。

该过程能够覆盖课程要求的至少两轮完整迭代，并支持每个增量形成独立 Release。

## 20. 项目成功标准

- 组织者能够发布调研和志愿活动并查看匹配候选结果。
- 参与者能够通过匹配、报名或邀请完成一次预约。
- 取消预约后，系统能够正确执行候补补位且不会超员。
- 未授权用户无法访问联系方式和精确地点。
- 调研和志愿活动均能形成可查询的参与记录。
- 关键业务流程通过权限、并发和隐私测试。
- 三个增量均可部署并通过公网演示。
- 需求、设计、代码和测试保持可追溯。
