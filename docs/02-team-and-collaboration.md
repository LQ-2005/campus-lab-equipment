# 团队角色与协作机制

## 1. 分工原则

本项目为 4 人团队。角色分工需要覆盖：

- 项目经理。
- 需求分析师。
- 架构/设计工程师。
- 至少两名开发工程师。
- 测试/质量工程师。
- AI 使用负责人，可兼任。

## 5. 两轮迭代的评审交换

按照课程要求，两轮迭代之间至少交换一次结对或评审对象。

| 迭代 | 结对/评审安排 | 必须留痕 |
| --- | --- | --- |
| v0.1 | 首轮文档由固定复核人完成：冯昊天复核罗强文档，罗强复核冯昊天、付艺豪、张纪昆文档 | Issue、PR、评审意见、缺陷记录 |
| v0.2 | 冯昊天评审更新后的需求与计划；罗强评审测试设计与质量记录；付艺豪与张纪昆交换评审对象 | 不同评审人的新评审记录 |
| v0.3 | 根据前两轮缺陷集中区域重新分配交叉测试，不得由模块作者独立完成最终验收 | 验收记录、缺陷关闭证据 |

评审意见需要指出具体问题、所在文档或代码位置、处理责任人和关闭结果，不能只写“已检查”。

## 6. 防搭便车机制

每轮迭代记录以下证据：

- Git 提交作者、提交次数和实际变更内容。
- Issue 领取、完成和评审记录。
- PR 作者、评审人和修改记录。
- 调研、文档、测试和演示的分工。
- 组内贡献互评分数，范围 0-10 分。
- 迭代会议与答辩参与记录。

贡献评价按任务完成质量、协作、评审和技术产出综合判断，不单独使用代码行数或提交次数。

## 7. 任务发布与分派

罗强作为项目经理，统一负责计划内任务的创建和发布。其他成员不直接创建已确认的开发任务，而是先提交问题、缺陷或变更请求，由罗强甄别后进入任务池。

每个正式任务 Issue 必须由罗强确认以下字段：

- 任务目标和背景。
- 任务类型：需求、开发、测试、文档、缺陷或变更。
- 唯一负责人。
- 所属模块。
- 验收条件。
- 对应 Milestone 和 Project 状态。
- 前置任务和依赖。
- 固定评审人。
- 计划完成时间。

正式任务统一使用以下流程：

```text
罗强创建并发布 Issue
  -> 指派负责人
  -> 加入 Projects 的 To Do
  -> 负责人开始工作并移动到 In Progress
  -> 负责人提交分支和 PR
  -> 固定评审人审核
  -> CI 通过
  -> 罗强确认验收条件
  -> 合并并关闭 Issue
  -> Projects 移动到 Done
```

成员发现问题时仍可以在 GitHub 创建 Issue，但初始状态必须为 `status:triage`。罗强负责：

- 判断是否为重复问题。
- 确认是否属于当前增量。
- 明确负责人和验收条件。
- 将确认后的任务加入对应 Milestone 和 Projects。
- 对不接受的问题说明关闭原因。

罗强本人承担开发或文档任务时，由固定复核人独立审核和验收，避免自己发布、自己实现、自己批准。任何任务不得只在群聊中分派；群聊可以讨论，但最终任务要求和结论必须回到 Issue。

### 罗强本人任务的评审与合并

| 任务类型 | 固定评审人 | 合并操作建议 |
| --- | --- | --- |
| 项目文档、章程、团队管理、选题材料 | 冯昊天 | 冯昊天批准后执行合并 |
| 需求、用例、测试计划和质量记录 | 冯昊天 | 冯昊天批准后执行合并；冯昊天为作者时改由罗强复核 |
| 架构、数据库、接口和参与机会匹配代码 | 付艺豪 | 付艺豪批准后执行合并 |
| 预约、候补、签到、隐私和通知模块代码 | 张纪昆 | 张纪昆批准后执行合并 |
| 跨多个模块的集成改动 | 付艺豪或张纪昆主审，冯昊天复核测试影响 | 主评审人批准后由非作者合并 |

GitHub 不允许罗强批准自己的 PR。评审人选择 `Approve` 后，由该评审人或另一名非作者执行 `Create a merge commit`。如果固定评审人无法参加，应指定同等角色的替补评审人，并在 PR 中记录替补原因。

## 8. 协作流程

```text
创建 Issue
  -> 明确负责人和验收条件
  -> 从 main 创建功能分支
  -> 提交代码或文档
  -> 创建 Pull Request
  -> 至少一名非作者评审
  -> 通过 CI 并处理意见
  -> 合并到 main
  -> 更新 Projects
```

团队成员不得直接向 `main` 推送功能提交。计划和紧急修复也应在 PR 或 Issue 中说明原因。

## 9. AI 使用负责人

AI 使用负责人可兼任，主要工作是：

- 登记使用了哪些 AI 工具及用途。
- 保存关键提示词、AI 输出、人工修改和最终结果。
- 确认需求、设计、代码、测试和文档由成员审核。
- 检查是否将未核实内容直接写入需求或代码。
- 维护 AI 使用报告和“人在关卡”记录。

AI 不能替代真实访谈、测试执行、评审签字和责任确认。
