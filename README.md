# 研愿：校园调研与志愿活动平台

面向校园调研组织者、志愿活动组织者和参与者，根据兴趣、能力、资格与空闲时间匹配参与机会，并支持报名、预约、候补、签到和完成记录。

当前阶段为选题调整与需求调研准备。原“校园实验室设备预约与运维管理系统”选题保留在 Git 历史和既有 Issue 中，不删除、不改写历史记录。

- 当前阶段：新选题待教师审核

- 部署目标：公网可访问，用户通过浏览器使用

## 建设目标

1. 统一发布校园调研项目和志愿活动，减少信息分散。
2. 通过参与偏好、资格规则和空闲时间完成双向匹配。
3. 支持报名、定向邀请、预约确认、候补补位和签到。
4. 通过渐进披露保护参与者联系方式与精确地点。
5. 形成可追溯的调研参与记录和志愿服务记录。
6. 提供三种清晰且必要的用户角色与后端权限控制。

## 系统用户角色

| 角色 | 主要权限 | 明确限制 |
| --- | --- | --- |
| 参与者 | 维护兴趣、技能和空闲时间；发现或接受匹配；报名、预约、取消、签到；查看个人参与记录 | 不能查看其他参与者敏感信息或组织者后台 |
| 组织者 | 发布调研或志愿活动；设置资格和时段；查看匿名候选；确认报名和完成；管理候补 | 只能管理自己的机会，未经授权不能查看隐私字段 |
| 平台运营者 | 审核发布权限；管理分类与公共规则；处理举报和异常；查看审计和平台统计 | 不能无审计记录地修改预约结果或公开用户隐私 |

## 第一版范围

- GitHub OAuth 和邮箱注册登录。
- 参与者兴趣、技能、资格和空闲时间档案。
- 调研项目与志愿活动统一发布、检索和详情展示。
- 资格与时间匹配、匿名候选池和定向邀请。
- 报名、预约、确认、取消和候补自动补位。
- 签到、完成确认、调研参与记录和志愿服务记录。
- 字段级隐私授权、通知、举报、审计和基础统计。
- 自动化测试、CI/CD 与 Docker Compose 公网部署。

## 暂不实现

- 问卷答案、访谈录音、视频或实验数据的存储。
- 学校官方志愿时长认证和教务、学生档案集成。
- 真实支付、劳务费用和商品交易。
- 公开聊天广场、内容流或社交关系链。
- AI 自动决定报名资格或代替组织者确认完成。

## 计划增量

### v0.1 参与机会与偏好

- 用户、角色和基础权限。
- 参与者偏好档案。
- 调研与志愿活动统一发布。
- 分类检索、列表和详情展示。

验收标准：组织者能够发布两种参与机会，参与者能够筛选和查看，越权操作被拒绝。

### v0.2 匹配、预约与候补

- 资格和空闲时间匹配。
- 匿名候选池与定向邀请。
- 报名、确认、取消和名额锁定。
- 候补队列与自动补位。
- GitHub OAuth 外部登录。

验收标准：不符合条件的用户不能预约；同一时段不得超员；取消后能够正确补位。

### v0.3 参与记录、治理与部署

- 签到、完成确认和参与记录。
- 字段级隐私授权与访问审计。
- 招募漏斗、通知和统计。
- 组织者审核、举报和平台规则。
- 自动化测试、CI/CD、部署和演示脚本。

验收标准：未授权用户不能访问隐私字段；两类机会均能形成参与记录；系统能通过公网地址完整演示。

| 层次 | 技术 |
| --- | --- |
| 后端 | Java 21、Spring Boot 3、Spring Security |
| 数据访问 | Spring Data JPA 或 MyBatis-Plus |

| 前端 | Vue 3、Vite |

| 部署 | Docker Compose、Nginx |

技术栈可在设计评审后调整，调整结果应记录在架构决策记录中。

## 关键业务规则

- 同一参与时段的有效预约人数不能超过容量。
- 参与者只能管理自己的报名、预约和隐私授权。
- 组织者只能管理自己发布的机会。
- 确认预约前不得向组织者披露未授权联系方式或精确地点。
- 取消或邀请超时后，候选者只能获得一个有效名额。
- 调研和志愿活动的完成确认规则可以不同，但均须留痕。

## 外部集成与部署

使用 GitHub OAuth 作为第三方登录点，同时保留普通邮箱注册。系统不依赖学校统一身份认证或教务系统。

前端、后端、数据库和反向代理通过 Docker Compose 部署在同一台公网服务器。GitHub Actions 执行测试与构建，每个增量创建对应 Release。

## 主要技术风险

并发预约与候补补位一致性是首要技术风险。两个参与者可能同时接受最后一个名额，或者取消操作与自动补位同时发生。

拟采用的处理方式：

- 在数据库事务中检查并占用名额。
- 使用版本号或条件更新避免超员。
- 使用显式状态机控制邀请、确认、取消和超时。
- 对关键隐私字段执行字段级授权和访问审计。
- 编写并发与权限集成测试。

## 协作规范

1. 每个功能或需求变更通过 Issue 描述。
2. 功能分支通过 Pull Request 合并到 `main`，禁止直接推送。
3. 每个 PR 至少由一名非作者评审，CI 通过后合并。
4. 提交信息采用 `feat:`、`fix:`、`docs:`、`test:`、`chore:` 等前缀。
5. 不提交密码、API Key、数据库凭据和未脱敏调研材料。
6. 需求、设计、代码和测试必须保留可追溯编号。
7. 两轮迭代之间至少交换一次结对或评审对象。
8. 每轮记录提交、Issue、PR、评审和组内贡献证据。
