## 2. 调研目标

本调研服务于“校园调研与志愿活动平台”的 v0.1 需求基线，重点回答：

1. 学生目前如何发现并参加调研或志愿活动，主要依赖哪些渠道。
2. 组织者如何发布机会、筛选参与者、确认时间和处理候补。
3. 哪些信息在确认参与前不应公开，参与者实际担心哪些隐私风险。
4. 调研与志愿活动是否具有统一的发现、报名和记录需求。
5. 哪些能力属于 v0.1 必须交付，哪些可推迟到 v0.2、v0.3。
6. 用户对预约确认、取消和候补通知的渠道、时机和内容有哪些要求。

调研结论必须区分用户事实、用户原话和团队推断，不能把推断写成已证实需求。

## 3. 待验证假设

| 编号 | 假设 | 验证方式 |
| --- | --- | --- |
| H1 | 调研和志愿活动的机会信息分散，参与者难以持续发现适合自己的机会 | 参与者访谈、问卷 |
| H2 | 组织者需要人工筛选资格并多次确认时间，招募管理成本较高 | 组织者访谈、流程还原 |
| H3 | 确认参与前公开联系方式或精确地点，会降低部分参与者的参与意愿 | 参与者访谈 |
| H4 | 取消或缺席后人工寻找替补耗时，公开候补和自动补位具有价值 | 组织者访谈 |
| H5 | 参与者愿意维护一次兴趣、技能和空闲时间，用于两类机会的持续匹配 | 参与者访谈、原型测试 |
| H6 | 不同组织者为调研和志愿活动重复收集相似信息，统一参与记录具有价值 | 组织者访谈 |
| H7 | 用户不能始终停留在平台内，邀请、确认、取消和候补需要邮件等主动通知 | 参与者与组织者访谈、问卷 |

假设被推翻时必须保留证据并解释原因，不得为了支持方案修改用户原话。

## 4. 调研对象与配额

| 对象 | 代号 | 目标人数 | 关注重点 |
| --- | --- | --- | --- |
| 参加过校园调研或志愿活动的学生 | S1–S6 | 5–6 | 发现渠道、参与条件、隐私、取消和记录 |
| 组织过课程调研、访谈或志愿活动的人员 | O1–O3 | 2–3 | 发布、筛选、确认、候补和完成记录 |
| 负责内容审核或名单管理的人员 | A1–A2 | 1–2 | 权限、举报、数据处理和平台运营 |

访谈对象必须来自真实校园场景。仓库内只保留角色代号，真实姓名、学号、工号和联系方式不进入版本库。

## 5. 调研方法

| 方法 | 对象 | 用途 |
| --- | --- | --- |
| 半结构化访谈 | 参与者、组织者、运营人员 | 还原最近一次真实经历，识别痛点和异常 |
| 流程还原 | 组织者和参与者 | 还原“发布—发现—报名—确认—参与—记录”全流程 |
| 问卷 | 学生参与者 | 验证痛点频率和优先级；不能替代访谈 |
| 现有材料收集 | 组织者、运营人员 | 查看空白表单、群通知模板和名单结构；不收集含隐私的填报数据 |

提问围绕最近一次具体经历展开，避免只询问“你觉得需要什么功能”。

## 8. 重点访谈问题

### 参与者

1. 最近一次参加校园调研或志愿活动是什么时候，通过什么渠道得知？
2. 报名前需要确认哪些条件，哪些信息最难找到？
3. 需要重复填写哪些信息，是否希望保存为长期偏好？
4. 报名时是否愿意公开联系方式、专业、年级和精确地点？
5. 是否发生过资格不符、时间冲突、取消或未被通知？
6. 参加后是否有参与记录，记录来自哪里？
7. 你希望通过站内消息、邮件或其他方式收到邀请、确认、取消和候补通知？哪些信息必须包含？

### 组织者

1. 最近一次招募使用哪些工具，从发布到招满经历哪些步骤？
2. 如何判断参与者是否符合资格，花费多少时间？
3. 如何处理申请、确认、取消和候补？
4. 何时公开地点和联系方式，出现过哪些隐私或误解问题？
5. 如何记录实际参与和完成情况？
6. 调研与志愿活动的招募流程有哪些共同点与差异？
7. 当前如何通知邀请、确认、取消和候补？是否遇到过邮件失败、重复通知或用户未看到消息？

### 内容审核或名单管理人员

1. 哪些内容或组织者需要审核，审核依据是什么？
2. 如何处理举报、虚假活动、重复报名和异常账号？
3. 哪些操作必须保留日志？
4. 平台应避免收集哪些敏感数据？

## 9. 匿名化与数据保护

- 受访者姓名、学号、工号、手机号和微信号不进入仓库。
- 访谈纪要使用角色代号，院系和班级信息做泛化处理。
- 录音仅在单独同意后保存于本地受控目录，不进入 GitHub。
- 仓库只保存脱敏 Markdown 纪要和汇总结果。
- 禁止使用 AI 生成、补全或虚构访谈内容。

## 10. 证据与追溯

| 类型 | 编号格式 | 示例 |
| --- | --- | --- |
| 访谈问题引用 | 场次-问题号 | `S1-Q3` |
| 调研发现 | F-序号 | `F-01` |
| 用户故事 | US-序号 | `US-01` |
| 需求条目 | REQ-序号 | `REQ-01` |
| 用例 | UC-序号 | `UC-01` |
| 测试用例 | TC-序号 | `TC-01` |

追溯链：

```text
访谈证据
  -> 调研发现
  -> 用户故事及验收条件
  -> 需求条目
  -> 用例
  -> 测试用例
```

每条用户故事至少关联一条调研发现；团队推断必须明确标注依据。

## 12. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 受访者只谈抽象意见 | 无法得到真实痛点 | 追问最近一次经历和具体操作 |
| 样本集中在单一场景 | 结论偏差 | 同时覆盖调研和志愿活动，覆盖不同年级 |
| 隐私顾虑导致回答失真 | 无法验证披露机制 | 使用代号、只做笔记、说明删除规则 |
| 组织者时间难约 | 缺少招募管理证据 | 准备短访谈和备选对象 |
| 把方案当成需求 | 需求基线失真 | 访谈前不展示功能列表 |
| 旧选题材料误用 | 证据链错误 | 旧记录明确归档为历史，不作为新需求证据 |

## 13. 变更与评审

- 本计划变更需在 Pull Request 中说明原因，由罗强重新评审。
- 访谈提纲的小幅优化记录在 PR 评论中；对象配额、匿名化或数据保存方式变化必须重新评审。
- 评审意见必须指出具体章节和问题，处理结果在 PR 中回复。
