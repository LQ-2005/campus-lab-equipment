## 2. 项目背景

高校实验室设备通常通过群聊、纸质表格或多个独立流程完成预约。设备空闲信息、预约审批、使用记录和维修状态分散在不同渠道，容易产生以下问题：

- 学生无法及时确认设备在目标时段是否可用。
- 同一设备可能被重复预约。
- 审批人与实际负责人不一致，流程难以追踪。
- 使用记录、故障报修和维修历史缺少关联。
- 设备停用或维修后，原有预约无法得到统一处理。

本项目建立统一的设备预约与运维管理系统，将设备、预约、使用、故障和维修状态连接成可追溯的业务流程。

## 3. 项目目标

### 3.1 业务目标

- 提供统一的实验室设备信息入口。
- 减少设备重复预约和人工协调。
- 规范预约审批、使用登记和维修处理流程。
- 形成可查询的设备使用与运维历史。
- 为后续实验规划 Agent 提供结构化业务接口。

### 3.2 工程目标

- 使用明确的角色权限控制不同用户操作。
- 通过状态机约束预约、设备和维修单的合法流转。
- 对关键操作保留审计记录。
- 使用自动化测试验证并发预约等关键风险。
- 形成可持续迭代、可部署的软件系统。

## 4. 用户与权限

| 角色 | 主要权限 |
| --- | --- |
| 学生 | 查询实验室和设备；提交、查看和取消自己的预约；登记使用；提交故障报修 |
| 教师 | 查看设备与预约；审批授权范围内的预约；查看相关使用记录 |
| 实验室管理员 | 维护实验室和设备；审批预约；处理报修；停用或恢复设备；查看统计和审计 |

权限判定由后端统一执行，前端隐藏按钮不能替代服务端鉴权。

## 5. 项目范围

### 5.1 范围内

- 用户登录和基于角色的访问控制。
- 实验室、设备分类和设备档案。
- 设备状态、存放位置和维护期限。
- 设备可用时段查询。
- 预约提交、审批、拒绝、取消和过期。
- 使用登记与归还。
- 故障报修、维修处理和维修记录。
- 邮件推送或站内通知。
- 基础统计、审计和系统管理。

### 5.2 范围外

- 真实仪器设备的联网控制。
- 自动判断设备能否继续安全运行。
- 在线支付与商业计费。
- 第一版直接实现全自动 Agent 调度。
- 替代实验室安全制度和人工审批。

## 6. 核心业务流程

### 6.1 预约流程

```text
学生查询设备
  -> 选择空闲时段
  -> 填写用途与使用人数
  -> 提交预约
  -> 教师或实验室管理员审批
  -> 批准后等待使用
  -> 使用前登记
  -> 使用完成或异常结束
```

预约状态至少包括：

```text
DRAFT -> PENDING -> APPROVED -> CHECKED_IN -> COMPLETED
                    |              |
                    -> REJECTED     -> CANCELLED
                    -> EXPIRED      -> NO_SHOW
```

### 6.2 运维流程

```text
用户或管理员发现故障
  -> 提交报修
  -> 管理员受理
  -> 设备进入维修状态
  -> 维修处理
  -> 验收
  -> 设备恢复可用或停用
```

设备状态至少包括：

```text
AVAILABLE
RESERVED
IN_USE
MAINTENANCE
DISABLED
RETIRED
```

## 7. 可交付增量

### 7.1 v0.1 预约主流程

交付内容：

- 用户、角色和权限。
- 实验室与设备档案。
- 设备可用时段查询。
- 预约提交、审批和取消。
- 基础审计日志。

验收条件：

- 学生能够完成一次预约。
- 管理员能够批准或拒绝预约。
- 越权用户无法操作他人预约。
- 同一设备不能产生重复的有效预约。

### 7.2 v0.2 使用与维修

交付内容：

- 使用前登记和完成登记。
- 设备状态历史。
- 故障报修和维修工单。
- 维修完成后的设备恢复。

验收条件：

- 设备能够完成预约、使用和归还流程。
- 设备能够完成故障、维修和恢复流程。
- 每条关键状态变化都有操作人和时间记录。

### 7.3 v0.3 通知、治理与部署

交付内容：

- 邮件或站内消息通知。
- 并发预约冲突处理。
- 统计和审计功能完善。
- 自动化测试、CI 和部署说明。

验收条件：

- 系统能够部署运行。
- 关键业务和权限场景有自动化测试。
- GitHub Actions 能够完成构建和测试。
- 通知失败不会破坏预约主流程。

## 8. 外部集成点

第一版选择第三方邮件服务作为正式外部集成点，用于发送：

- 新预约审批提醒。
- 预约批准、拒绝和取消通知。
- 设备维护到期提醒。
- 维修处理结果。

邮件服务通过独立适配器封装，密钥只通过环境变量提供。服务不可用时，通知进入待重试状态，不阻塞预约事务。

## 9. 非功能需求

### 9.1 安全性

- 所有业务接口必须经过认证和授权。
- 密码必须使用安全哈希保存。
- 日志不得记录密码、令牌和完整邮件密钥。
- 调研材料中的个人信息必须脱敏。

### 9.2 一致性

- 预约冲突检测必须在服务端完成。
- 状态变化必须符合状态机。
- 关键写操作使用数据库事务。

### 9.3 可追溯性

- 预约审批、设备状态和维修处理保留操作记录。
- 需求、设计、代码、测试和 Issue 使用统一编号关联。

### 9.4 可用性

- 设备查询和预约流程应提供明确错误提示。
- 通知失败时应保留可重试记录。
- 后端异常不能导致预约状态部分更新。

## 10. 技术风险

### 主要风险：并发预约冲突

两个用户可能同时查询到同一空闲时段，并在提交请求时同时通过前端校验。

处理措施：

- 在后端事务中锁定设备记录。
- 锁定后重新查询时间重叠。
- 使用幂等键避免重复提交。
- 通过集成测试模拟并发请求。

### 次要风险

- 设备状态与预约状态不一致。
- 邮件服务不可用。
- 管理员误操作导致设备被错误停用。
- 后续 Agent 调用工具时出现重复执行或越权。

## 11. 过程模型

项目采用增量式开发，并在每个增量内进行“计划—构建—测试—评审”迭代。

选择原因：

- 业务对象和权限流程适合逐步完善。
- 每个增量都能形成可演示版本。
- 并发、通知和部署问题可以在后续迭代集中处理。
- 符合课程对多次迭代和 GitHub 过程留痕的要求。

## 13. 项目成功标准

- 三个增量均形成可运行、可评审版本。
- 预约、使用和维修主流程状态清晰且可追溯。
- 权限、并发预约和通知失败场景经过测试。
- 关键文档与代码能够通过需求编号相互追溯。
- 系统可以在标准环境中完成部署和演示。
