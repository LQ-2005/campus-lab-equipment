# 外部集成规范

## 1. 目的

本文档统一“研愿：校园调研与志愿活动平台”的外部集成边界，当前包括：

1. GitHub OAuth 第三方登录。
2. 第三方邮件通知服务。

两项集成都由后端适配器封装，浏览器、业务领域模型不得直接依赖具体服务商。

## 2. 集成清单

| 集成点 | 用途 | 是否阻塞核心事务 | 失败降级 |
| --- | --- | --- | --- |
| GitHub OAuth | 第三方身份认证 | 是，登录流程本身需要完成授权 | 用户改用邮箱注册或登录 |
| 第三方邮件服务 | 邀请、确认、取消、候补和完成通知 | 否 | 保存待发送记录并重试，站内通知仍可用 |

## 3. GitHub OAuth

### 3.1 使用范围

- 用户通过 GitHub 授权登录。
- 只请求平台展示身份所需的最小范围，不读取用户仓库内容。
- OAuth 仅用于登录，不用于提交代码、修改仓库或代替用户执行 GitHub 操作。

### 3.2 基本流程

```text
用户选择 GitHub 登录
  -> 跳转 GitHub 授权
  -> GitHub 回调平台
  -> 后端校验 state 并交换授权码
  -> 获取最小身份信息
  -> 建立或绑定平台账号
  -> 建立平台会话
```

### 3.3 安全要求

- `state` 必须随机生成并一次性校验，防止回调伪造。
- GitHub Client Secret 只保存在后端环境变量中。
- 不在日志中记录授权码、访问令牌和完整回调参数。
- 允许用户使用邮箱注册或登录，避免 OAuth 故障阻断全部用户。
- 解绑 GitHub 账号前必须保证用户仍有可用的登录方式。

## 4. 第三方邮件通知服务

### 4.1 通知场景

- 收到定向邀请。
- 预约确认或拒绝。
- 活动取消或改期。
- 候补自动递补邀请。
- 邀请即将过期。
- 参与完成确认。

站内通知是邮件通知的业务来源；邮件只是额外送达渠道，不改变预约状态。

### 4.2 发送原则

- 预约、确认、取消和候补事务先提交，再创建邮件任务。
- 邮件发送失败不得回滚业务事务。
- 同一业务事件使用稳定的幂等键，避免重复发送。
- 邮件任务保存收件人、模板、业务事件、尝试次数、最后错误和计划发送时间。
- 默认采用短超时和有限重试，超过最大次数后标记为人工处理。
- 邮件模板只能使用业务事件所需字段，不包含未授权的联系方式、精确地点或调研材料。

### 4.3 Outbox 状态

```text
PENDING -> SENDING -> SENT
                 \-> FAILED -> PENDING（重试）
                            \-> DEAD（超过重试上限）
```

### 4.4 幂等与重试

- 幂等键示例：`invitation:{invitationId}:created`。
- 同一幂等键已经发送成功时，不再重复投递。
- 服务商返回可重试错误时按退避策略重新排队。
- 参数错误、模板错误或明确拒收等不可重试错误直接进入失败记录。

### 4.5 配置与密钥

建议通过环境变量提供以下配置，具体名称由架构设计确认：

- `GITHUB_CLIENT_ID`
- `GITHUB_CLIENT_SECRET`
- `MAIL_PROVIDER_BASE_URL`
- `MAIL_API_KEY`
- `MAIL_FROM_ADDRESS`

任何密钥、令牌或真实邮件地址都不得提交到 Git 仓库。

## 5. 测试要求

- 使用 Mock 邮件适配器测试发送成功、超时、限流、不可重试错误和重复回调。
- 验证邮件失败时预约、取消和候补事务仍正确提交。
- 验证同一业务事件不会被重复发送。
- 验证邮件模板不包含未授权敏感字段。
- 验证 GitHub OAuth 的 `state` 校验、回调失败和邮箱登录降级。

## 6. 验收条件

- GitHub OAuth 和邮箱登录均可用。
- 指定业务事件能够生成站内通知和邮件通知。
- 邮件服务不可用时预约主流程不受影响。
- 邮件失败可重试，重复事件不会重复发送。
- 密钥不出现在前端、日志和版本库中。
- 外部集成的接口契约、错误处理和测试记录可追溯。
