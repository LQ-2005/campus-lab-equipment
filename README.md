# 校园实验室设备预约与运维管理系统

面向学生、教师和实验室管理员，提供实验室设备查询、预约审批、使用登记、故障报修和设备运维管理。

项目先完成可运行的传统管理系统，再在稳定的业务底座上扩展实验规划与运维 Agent。当前阶段聚焦选题立项、需求调研和第一版范围确认。

## 项目状态

- 当前阶段：选题与需求调研
- 首个里程碑：`v0.1` 设备预约主流程
- 状态：待教师审核选题
- 技术方向：Java 后端

## 建设目标

1. 将分散的设备信息和预约流程集中到统一系统。
2. 支持学生查询设备空闲时段并提交预约。
3. 支持教师或实验室管理员审批预约。
4. 记录设备使用、故障和维修过程。
5. 通过角色权限和操作审计保证流程可追溯。
6. 为后续实验规划 Agent 提供稳定、结构化的业务接口。

## 第一版范围

- 用户登录、角色和权限管理。
- 实验室与设备档案管理。
- 设备可用时段查询。
- 预约提交、审批、拒绝、取消和过期。
- 使用前登记与使用完成登记。
- 故障报修、维修处理和设备状态管理。
- 邮件或站内消息通知。
- 基础统计、测试和部署说明。

## 暂不实现

- 真实仪器硬件控制。
- 自动判断设备是否安全。
- 在线支付和商业计费。
- 未经审核的全自动设备调度。
- 第一版直接接入大模型 Agent；Agent 作为后续创新增量实现。

## 计划增量

### v0.1 预约主流程

- 用户、角色、权限。
- 实验室、设备分类和设备档案。
- 空闲时段查询。
- 预约、审批、拒绝、取消。
- 基础审计日志。

验收标准：学生能够完成一次设备预约，管理员能够审批，越权操作被拒绝。

### v0.2 使用与运维流程

- 使用登记和归还。
- 设备状态流转。
- 故障报修、维修受理和关闭。
- 维修记录和设备停用。

验收标准：设备能够经历“可用—预约—使用—归还”或“故障—维修—恢复可用”的完整状态变化。

### v0.3 通知、治理与部署

- 邮件或站内消息通知。
- 并发预约冲突处理。
- 统计报表和操作审计完善。
- 单元测试、集成测试、CI 和部署文档。

验收标准：形成可部署版本，关键流程具备自动化测试和 GitHub Actions 检查。

## 关键业务规则

- 同一设备在有效预约时段内不能存在两个有效占用。
- 学生只能管理自己的预约。
- 教师只能审批有权限处理的预约。
- 实验室管理员可以维护设备和处理维修，但关键操作必须留痕。
- 已开始使用的预约不能直接删除，只能进入完成、异常或取消流程。
- 停用设备不能被新预约。

## 外部集成点

第一版采用第三方邮件推送或站内消息服务，用于预约审批、设备维护提醒和维修结果通知。邮件密钥通过环境变量注入，不进入版本库。

## 主要技术风险

并发预约冲突是首要技术风险。两个用户可能同时查询到同一空闲时段，并在提交预约时同时通过校验。

拟采用的处理方式：

- 在后端事务内执行冲突检测。
- 锁定目标设备记录后再次检查重叠预约。
- 使用幂等请求避免重复提交。
- 预约状态变化使用明确的状态机。
- 对并发场景编写集成测试。

## 协作规范

1. 每个功能通过 Issue 描述。
2. 功能分支使用 `feature/<issue-number>-<name>`。
3. 通过 Pull Request 合并到 `main`，禁止直接推送到主分支。
4. 提交信息采用 `feat:`、`fix:`、`docs:`、`test:`、`chore:` 等前缀。
5. 不提交密码、API Key、数据库凭据和包含个人信息的调研原始材料。
6. 需求、设计和测试记录必须保留可追溯编号。
7. 两轮迭代之间至少交换一次结对对象或评审对象。
8. 每轮记录 Git 提交人数与工作量、Issue/PR 贡献、评审记录和 0-10 分组内互评分。
9. 计划内任务统一由罗强创建和指派；其他成员提交的问题先进入待甄别状态，不能只在群聊中分派任务。
