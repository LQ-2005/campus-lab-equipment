# 用户故事 Issue 拆分草稿

本文件用于 Issue #12 的「Issue 化准备」。每条草稿可直接复制到 GitHub 新建 Issue，标题和正文都已按仓库习惯写好。

**用法**

1. 在 GitHub 新建 Issue，标题粘对应代码块第一行的标题。
2. 正文整体粘贴代码块内容。
3. Labels 建议：`feature` + 增量标签（`v0.1` / `v0.2` / `v0.3`）。
4. 每条 Issue 的固定评审人都是罗强（`LQ-2005`）。

**统一约定**

- 关联上游：Issue #12（用户故事）、`docs/research/findings.md`（Issue #11）。
- 验收标准一律为 Given / When / Then，可直接转成测试用例。
- 标「待补 REQ」的条目，需先在需求基线评审中确认编号，再开始开发。

## 1. 用户、角色与基础权限

```markdown
# [v0.1] 用户、角色与基础权限

## 关联

- 用户故事：US-23（角色部分）、US-01 ~ US-22 的前置
- 需求：REQ-06
- 上游：Issue #12、`docs/requirements/user-stories.md`

## 背景

所有后续功能都依赖统一的身份与角色判定。三种角色（参与者、组织者、平台运营者）的权限必须由后端判定，前端只做展示。

## 范围

- 用户注册与登录（邮箱 + 密码）
- 三种角色的数据模型与权限矩阵
- 越权访问统一返回 403，并记录审计信息

## 验收标准

1. Given 未登录用户，When 访问需要登录的接口，Then 返回 401。
2. Given 参与者身份，When 调用组织者专属接口，Then 返回 403。
3. Given 平台运营者身份，When 访问运营接口，Then 正常返回。
4. Given 普通注册用户，When 首次登录，Then 必须选择角色后才能继续。

## 非范围

- GitHub OAuth（见另一条 Issue）
- 角色申请与审批流程

## 依赖

无。本 Issue 是其余所有 Issue 的前置。
```

## 2. 参与者偏好档案与报名信息复用

```markdown
# [v0.1] 参与者偏好档案与报名信息复用

## 关联

- 用户故事：US-01、US-02
- 调研发现：F-03（S3 每次报名重复填写年级、专业、空闲时间、联系方式）
- 需求：REQ-03、REQ-08
- 上游：Issue #12

## 背景

参与者每参加一次活动就要重填一遍基础信息，填写慢还会导致名额被抢完（S3）。需要一次维护、长期复用。

## 范围

- 偏好档案：兴趣、技能、可参与时段
- 基础信息：年级、专业、联系方式
- 报名表单预填与本次值覆盖

## 验收标准

1. Given 未填写档案，When 打开偏好设置，Then 显示兴趣、技能、可参与时段三个分区并标明必填项。
2. Given 保存成功，When 重新登录，Then 回显已保存内容。
3. Given 档案完整，When 报名某活动，Then 自动预填基础信息，且本次可单独修改。
4. Given 在报名表单中修改了预填值，When 提交成功，Then 档案中的值不被覆盖。
5. Given 档案缺报名必填项，When 提交报名，Then 拒绝并提示需要补齐的字段。

## 依赖

- 用户、角色与基础权限
```

```markdown
## 背景

活动信息 100% 依赖微信群，新人不在群里就没有任何入口（S1）。平台必须先提供一个不依赖加群的统一入口。

3. Given 筛选无结果，Then 显示空状态而不是报错。
4. Given 打开活动详情，Then 展示全部参与条件；组织者未填的必填字段显示"未提供"。
5. Given 已过报名截止时间，Then 详情页显示截止并禁用报名入口。

## 依赖

- 用户、角色与基础权限
- 统一发布模板（详情字段来源）
```

## 5. 资格匹配与匿名定向邀请

```markdown
# [v0.2] 资格匹配与匿名定向邀请

## 关联

- 用户故事：US-06、US-07
- 调研发现：F-04（资格不透明导致不敢报）、F-10（确认前不应暴露联系方式）
- 需求：REQ-07、待补 REQ-17
- 上游：Issue #12

## 背景

参与者要在翻完所有公告后才能判断自己合不合适（S4）；组织者也需要主动找到符合条件的人，而不是等群里碰运气（O1）。同时确认前不能暴露联系方式（A2）。

## 范围

- 基于偏好档案的资格与空闲时间匹配
- 匿名候选池（只展示年级、专业、技能标签）
- 定向邀请、接受、拒绝与过期
- 受邀接受后直接生成报名

## 验收标准

1. Given 档案完整，When 打开"适合我的机会"，Then 只显示资格满足且时段有交集的机会。
2. Given 资格不满足，Then 该机会不出现在匹配列表，但仍可在全量列表中检索到。
3. Given 组织者打开候选池，Then 只看到匿名摘要，不含姓名、手机号、微信号。
4. Given 受邀者接受邀请，Then 直接生成报名并锁定名额。
5. Given 受邀者拒绝或邀请过期，Then 名额释放，不留下负面记录。

## 待确认

REQ-17（匿名候选池与定向邀请）在 findings 的 REQ 清单中尚无编号，需在需求基线评审中确认。

## 依赖

- 参与者偏好档案与报名信息复用
- 报名、名额锁定与取消
```

## 6. 报名、名额锁定与取消

```markdown
# [v0.2] 报名、名额锁定与取消

## 关联

- 用户故事：US-08、US-09
- 调研发现：F-03（填写耗时导致名额被抢）、F-08（取消后补位困难）
- 需求：REQ-08
- 上游：Issue #12

## 背景

名额有限且抢手，必须保证同一时段不超员；参与者也需要能主动取消，把名额让出来。

## 范围

- 报名、确认、剩余名额扣减
- 并发报名的名额锁定（事务内条件更新）
- 活动开始前取消与名额释放
- 报名状态机（待确认、已确认、已取消、已完成）

## 验收标准

1. Given 名额有剩余且资格满足，When 提交报名，Then 状态为已确认，剩余名额减 1。
2. Given 名额已满，When 提交报名，Then 拒绝并提示可加入候补。
3. Given 两人同时争抢最后一个名额，When 都提交，Then 只有一人成功，另一人收到"名额已满"。
4. Given 报名已确认且活动未开始，When 取消，Then 状态变为已取消，名额立即释放。
5. Given 活动已开始，When 尝试取消，Then 拒绝并提示联系组织者。

## 依赖

- 用户、角色与基础权限
- 机会检索与详情展示
```

## 7. 候补队列与自动补位

```markdown
# [v0.2] 候补队列与自动补位

## 关联

- 用户故事：US-10、US-11
- 调研发现：F-08（O2 每次活动 2–3 人取消，人工补位 2–3 小时）、F-02
- 需求：REQ-09、REQ-13
- 上游：Issue #12

## 背景

组织者现在只能回群里重新发"急招"，每次补位要 2–3 小时，活动前临时取消常常来不及（O2）。

## 范围

- 候补队列、排队序号、主动退出
- 取消后按序自动补位
- 补位确认有效期与顺延
- 补位结果通知（站内，邮件在 v0.3）

## 验收标准

1. Given 名额已满，When 加入候补，Then 获得可见的排队序号。
2. Given 已在队列，When 再次加入，Then 提示已在队列，不重复入队。
3. Given 主动退出候补，Then 队列移除，后续序号前移。
4. Given 队列非空且有人取消，Then 第一顺位自动转为已确认，组织者名单同步更新。
5. Given 第一顺位未在有效期内确认，Then 顺延给下一顺位并记录原因。

## 依赖

- 报名、名额锁定与取消
```

## 11. 站内通知与邮件通知（Outbox）

```markdown
# [v0.3] 站内通知与邮件通知（Outbox）

## 关联

- 用户故事：US-16、US-17
- 调研发现：F-02（S2 微信群无提醒错过名额）
- 需求：REQ-13
- 规范：`docs/04-external-integrations.md`（Outbox、重试、幂等、失败不阻塞）
- 上游：Issue #12

## 背景

用户不能一直停在平台里，关键事件需要主动通知；但邮件是设计选择，访谈只证明"需要主动通知"。

## 范围

- 站内通知与未读数
- 邮件通知：邀请、确认、取消、候补递补、完成
- Outbox 异步发送、退避重试、幂等键
- 发送失败列表与告警

## 验收标准

1. Given 关键事件发生，Then 相关方收到站内通知，入口显示未读数。
2. Given 已读通知，Then 未读数相应减少。
3. Given 用户开启邮件通知且邮箱已验证，Then 通过 Outbox 异步发送，主流程不等待结果。
4. Given 邮件服务不可用，Then 报名、取消、候补照常提交，邮件进入待重试。
5. Given 同一事件重复触发，Then 幂等键保证只发送一次。
6. Given 连续失败超过阈值，Then 运营后台显示失败列表和原因。

## 依赖

- 报名、名额锁定与取消
- 候补队列与自动补位
```

## 12. 字段级隐私授权与导出审计

```markdown
# [v0.3] 字段级隐私授权与导出审计

## 关联

- 用户故事：US-20、US-21
- 调研发现：F-10（A2 名单存共享云盘、无分级无日志、曾误发闲置群）
- 需求：REQ-12
- 上游：Issue #12

## 背景

确认参与前公开联系方式会带来真实泄漏风险：A2 的名单 Excel 曾被误发到无关微信群，花 1 小时才撤销。

## 范围

- 手机号、微信号、家庭住址的字段级可见性
- 确认前后、活动结束后不同阶段的披露规则
- 导出权限校验与审计日志

## 验收标准

1. Given 尚未确认参与，When 他人查看详情或名单，Then 看不到手机号、微信号、家庭住址。
2. Given 已确认参与，Then 仅该活动组织者可见必要联系方式。
3. Given 活动结束超过保留期，Then 联系方式自动失效。
4. Given 无导出权限，Then 不显示导出入口，直接调接口返回 403。
5. Given 完成导出，Then 记录操作人、时间、字段范围和条数。
6. Given 访问非本人负责活动的名单，Then 拒绝并写审计日志。

## 依赖

- 用户、角色与基础权限
- 报名、名额锁定与取消
```

## 13. 活动审核、举报与运营统计

```markdown
# [v0.3] 活动审核、举报与运营统计

## 关联

- 用户故事：US-18、US-19
- 证据：A1-Q1、A1-Q2、A1-Q3、A1-Q8、A1-Q9、A2-Q8
- 需求：待补 REQ-17、待补 REQ-18
- 上游：Issue #12

## 背景

运营者最担心冒充组织者骗信息和权限滥用（A1-Q9），也遇到过同一活动被重复发布（A1-Q2）。运营侧只需要数字，不要具体是谁（A1-Q8、A2-Q8）。

## 范围

- 发布前审核与驳回
- 举报受理、处理与留痕
- 重复发布提示
- 去标识化统计（报名、到场率、类型分布、年级比例）
- 小样本抑制

## 验收标准

1. Given 组织者提交发布，When 进入待审核，Then 运营者能看到字段完整性检查结果。
2. Given 信息不全或疑似虚假，When 驳回，Then 组织者收到带原因的驳回通知，活动不对外展示。
3. Given 收到举报，When 处理完成，Then 记录处理人、时间、结论。
4. Given 两个活动内容高度相似，Then 提示疑似重复发布。
5. Given 打开统计，Then 展示报名人数、到场率、类型分布、年级比例，且不含姓名、学号、手机号。
6. Given 某维度样本量低于阈值，Then 不展示该维度数值。

## 待确认

审核举报与运营统计在 findings 的 REQ 清单中没有编号，需先在需求基线评审确认 REQ-17、REQ-18。

## 依赖

- 统一发布模板
- 报名、名额锁定与取消
```
