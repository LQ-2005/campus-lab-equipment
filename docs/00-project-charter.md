## 2. 项目背景

校园调研和志愿活动通常通过群聊、共享文档、问卷链接和私聊组织。参与者难以持续发现适合自己的机会，组织者需要人工筛选报名者、协调时间并处理取消后的名额空缺。

本平台将两类活动统一抽象为“校园参与机会”，提供统一偏好、资格匹配、隐私授权、预约候补和参与记录能力。平台只处理招募与预约，不保存问卷答案、访谈录音、实验数据或官方志愿时长。

## 3. 项目目标

### 3.1 业务目标

- 将校园调研与志愿活动集中到统一入口。
- 根据兴趣、能力、资格和空闲时间进行双向匹配。
- 减少组织者人工筛选和重复协调。
- 在确认预约前保护参与者联系方式与精确地点。
- 通过候补自动补位降低取消和缺席造成的名额浪费。
- 形成可查询、可追溯的参与记录。

### 3.2 工程目标

- 建立三种边界清晰的系统用户角色。
- 使用状态机约束机会、报名、预约和候补流转。
- 对关键权限、隐私和状态变化保留审计记录。
- 使用自动化测试验证并发预约、越权访问和候选补位。
- 通过 Docker Compose 和 GitHub Actions 实现可重复部署。

## 4. 用户角色与权限

| 角色 | 核心权限 | 明确限制 |
| --- | --- | --- |
| 参与者 | 维护兴趣、技能和空闲时间；浏览机会；接受邀请或申请；预约与取消；签到；查看个人参与记录 | 不能查看其他参与者隐私，不能进入组织者后台 |
| 组织者 | 发布调研或志愿活动；配置资格、人数和时段；查看匿名候选；确认报名和完成；管理候补 | 只能管理自己的机会，未经授权不能查看联系方式或精确地点 |
| 平台运营者 | 审核发布权限；管理分类和规则；处理举报；查看平台统计和审计；执行账号治理 | 不能无审计记录地修改预约结果或公开用户隐私 |

权限由后端统一判定。用户可以在不同机会中承担不同角色，但每项操作仍受对应数据范围约束。

## 5. 项目范围

### 5.1 范围内

- GitHub OAuth 与邮箱注册登录。
- 参与者偏好、技能和空闲时间档案。
- 调研项目和志愿活动统一发布。
- 分类检索、资格匹配和匿名候选池。
- 定向邀请、报名、预约、确认、取消和候补。
- 签到、完成确认和参与记录。
- 字段级隐私授权、通知、举报和审计。
- 基础统计、自动化测试、CI/CD 和公网部署。

### 5.2 范围外

- 保存问卷原始答案、访谈录音、视频或实验数据。
- 学校官方志愿时长认证。
- 接入教务系统、学生档案或学校统一身份认证。
- 在线支付、劳务费用和商品交易。
- 公开聊天广场、社交内容流或推荐关系链。
- AI 自动决定资格或代替组织者确认完成。

## 6. 核心业务流程

```text
组织者发布调研或志愿活动
  -> 参与者维护兴趣、能力和空闲时间
  -> 系统执行资格与时间匹配
  -> 参与者报名或接受邀请
  -> 组织者确认并锁定名额
  -> 双方获得必要参与信息
  -> 参与者签到
  -> 组织者确认完成
  -> 形成调研或志愿服务参与记录
```

取消时，系统释放名额并向候补者发送限时邀请；邀请超时后继续邀请下一位。

## 7. 核心状态

### 7.1 参与机会

```text
DRAFT -> PUBLISHED -> FILLED -> IN_PROGRESS -> COMPLETED
                  \-> CANCELLED
```

### 7.2 报名或邀请

```text
INVITED -> APPLIED -> CONFIRMED -> CHECKED_IN -> COMPLETED
       \-> REJECTED
       \-> EXPIRED
       \-> CANCELLED

CONFIRMED -> NO_SHOW
```

状态变化必须由服务端校验，禁止前端直接修改。

## 8. 可交付增量

### v0.1 参与机会与偏好

- 用户认证、角色和基础权限。
- 参与者偏好与空闲时间档案。
- 调研和志愿活动统一发布。
- 分类检索、详情和基础隐私说明。

验收条件：组织者能发布两种机会；参与者能检索和查看；越权请求被拒绝。

### v0.2 匹配、预约与候补

- 资格规则与空闲时间匹配。
- 匿名候选池、定向邀请和报名。
- 预约确认、取消和名额锁定。
- 候补队列与自动补位。
- GitHub OAuth 外部登录。

验收条件：不符合资格的用户不能占用名额；并发接受最后一个名额不会超员；取消后能正确补位。

### v0.3 参与记录、治理与部署

- 签到、完成确认和参与记录。
- 字段级隐私授权与访问审计。
- 通知、招募漏斗、举报和平台规则。
- 自动化测试、CI/CD、部署和演示脚本。

验收条件：未授权用户无法访问隐私字段；两类机会均能形成参与记录；系统可通过公网地址完整演示。

## 9. 外部集成与部署

- 外部集成点：GitHub OAuth 第三方登录。
- 普通用户可通过邮箱注册，避免平台只服务 GitHub 用户。
- 后端：Java 21、Spring Boot 3、Spring Security。
- 前端：Vue 3、Vite。
- 数据库：PostgreSQL，数据库迁移使用 Flyway。
- 部署：Docker Compose、Nginx，运行于一台公网云服务器。
- 自动化：GitHub Actions 执行测试、构建和部署流水线。
- 不依赖学校教务、实验室、学生档案或志愿时长系统。

## 10. 非功能需求

### 10.1 安全性

- 所有业务接口必须认证并执行授权。
- 敏感字段按角色和预约状态动态披露。
- 密码使用安全哈希保存。
- 日志不得记录密码、令牌和完整联系方式。

### 10.2 一致性

- 名额接受使用数据库事务和原子条件更新。
- 取消、候补邀请和名额释放必须保持一致。
- 重复提交使用幂等控制。

### 10.3 隐私与可追溯性

- 未授权用户不能访问敏感字段。
- 关键权限、预约和状态变化记录操作者、时间和结果。
- 需求、设计、代码和测试保持可追溯。

## 11. 主要技术风险

### 11.1 并发预约与候补一致性

两个参与者可能同时接受最后一个名额，或者取消操作与自动补位同时发生。

应对措施：

- 在事务内检查并占用名额。
- 使用版本号或条件更新避免超员。
- 使用明确状态机控制邀请、确认、取消和超时。
- 编写并发集成测试。

### 11.2 隐私字段越权访问

组织者或普通用户可能通过接口访问隐藏的联系方式和精确地点。

应对措施：

- 执行字段级授权。
- 未经授权不向浏览器返回敏感字段。
- 对敏感字段访问写入审计日志。

### 11.3 虚假或低质量招募

- 组织者权限申请与运营审核。
- 举报、暂停和撤销发布权限。
- 公示参与规则与限制。

## 13. 过程模型

项目采用增量式开发，并在每个增量内进行“计划—构建—测试—评审”迭代。

选择原因：

- 参与机会发布、匹配预约和隐私治理适合分阶段交付。
- 每个增量都能形成可演示版本。
- 并发、候补和隐私风险可以在后续迭代集中验证。
- 便于根据真实访谈和阶段评审调整需求。

## 14. 项目成功标准

- 三个增量均形成可运行、可评审版本。
- 参与者可以完成一次机会发现、报名、预约、签到和记录流程。
- 组织者可以发布两类机会并管理名额与候补。
- 并发预约不会超员，取消后能够正确补位。
- 未授权用户无法访问隐私字段。
- 关键文档、代码和测试能够通过编号追溯。
- 系统可通过公网地址完成演示并具备自动化测试。
